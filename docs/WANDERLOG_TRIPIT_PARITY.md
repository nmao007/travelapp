## Interaction contract

- A traveler starts through search, a draggable globe, or reservation import. Search and globe resolve a **real destination object** with provider identity, coordinates and time zone. Search suggestions appear while typing; a globe tap yields actual nearby places, then selection leads to dates or dates-later. No required trip name.
- **Today** is the trip-time home: next proven commitment, useful map, a compact day, and at most a few relevant actions. No fake operational status. Before travel it shows preparation; after travel, unresolved follow-up.
- **Explore** is the source of discoverable real places, stays and bookable experiences. Every result has one primary action (save, add to day, or buy if a real provider supports it). A place detail sheet holds hours, source, directions, price/availability provenance and optional notes so the first screen stays quiet.
- **Trip** contains an ordered day view and an unscheduled **Saved** shelf. The map is a synchronized view of the same place objects; Reservations, Documents, Money, Checklists and collaborators are progressive sections in Trip, never independent copies of data. Desktop shows day and map together; phone shows the day first, with a map and detail sheet one tap away.
- **You** holds account, travelers, privacy, connections, offline downloads, notification settings and support. Only show options when functional, or label an unavailable integration honestly in internal development views.
- One place can be saved, assigned to a day, tied to a reservation, used in a route, and shared with tripmates without re-entering it. A booking is separate from a saved idea; a proposal is separate from a paid order. No payment or flight-status claim without an authorized provider.

TripIt adds operational depth beyond the attached Wanderlog list: [its current matrix](https://help.tripit.com/en/support/solutions/articles/103000063396-tripit-or-tripit-pro-) covers inbox-derived itineraries, calendar sharing, weather, airport maps, flight alerts, alternative flights, check-in/leave-time reminders, baggage/gates, documents, travel guidance, point/seat/fare tracking, risk alerts, trip sharing and mobile access. For us, importer/calendar/docs/flight/Today/airport coverage are core gates. Seat/fare/reward/flight-deal/safety-score features follow the core operational traveler loop and each needs its own provider, consent, source and notification contract; they must not be a generic “more” bucket or a fictional widget. Country-specific travel guidance depends on nationality, route and dated authoritative sources, and will be reviewed as high-stakes content before launch.

## Implementation slices, with stop points

1. **Now: destination discovery** — polished autocomplete, button to explore a real globe, click point → actual nearby destinations → existing date selection. Evidence: browser desktop/phone, attribution, no horizontal overflow, provider failure/empty cases, automated reverse validation. Pause for review.
2. **Next: single trip object and coherent Day/Saved/map** — normalize destination/place/idea/commitment/list/day IDs; migrate guest data without loss; edit/add multiple destinations; one-action POI save/day placement, reordering, bulk move/copy, notes/duration, compact view and map layers. Test round-trip persistence and cross-view identity. Pause for review.
3. **Next: genuine place discovery and useful Today** — licensed POI detail coverage, category chips, nearby by foreground location/manual area, short feasible proposal, source-timed route legs and fixed-booking protection; desktop/phone views. Pause.
4. **Next: bookings already made** — reviewed confirmation import (file/share/forward as each authorized channel comes online), typed reservations/tickets, duplicate/change resolution and secure storage. Wire flight feed and operational events into Today only after licensed data is available. Pause after each complete channel.
5. **Next: group and money** — authenticated cloud sync/RLS, roles/revocation, offline operation log, exact currency conversions, expense shares/settlement, checklist system, calendar/print/export. Native builds start against stable contracts; test same trip on real devices. Pause by vertical slice.
6. **Next: in-app transactions** — one supplier category at a time, starting with tour/activity; actual inventory and total quote through booking/payment/fulfillment/change/refund/support. Expand to stays and flights only after the first lifecycle and provider access pass. Pause after each supplier.
7. **Then: advanced parity and release** — road-trip/route optimization with preview/revert; guides/community with moderation; grounded assistant; flight alternatives, airport detail, price/reward monitoring; offline maps/tickets; real-trip beta, accessibility/performance/privacy/device/store gates. No app-store or production deployment without account/business access and final user approval.

Implementation prerequisites are tracked explicitly: Supabase administration is held by another person, so live migration, roles and cross-device sync cannot be verified yet. No booking, flight-status, rich POI-detail, routing or payment contract is connected. Photon public search is development-only; production requires `PHOTON_SERVICE_URL` for a hosted/self-managed instance. Nearby POIs currently use public Overpass by default; production needs a reliable permitted endpoint via `POI_SERVICE_URL` and availability monitoring. OpenFreeMap supplies the key-free web map style but no commercial support SLA. All incoming external data passes validation/provenance before storage; no scraped private competitor catalog, copied UI, imaginary inventory, or misleading “fully booked” state.
